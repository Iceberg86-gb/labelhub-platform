# W2 循环评测失败分析（ADR-019 v1）

| 项 | 值 |
|---|---|
| 基线 | [`runs/700607c95f112de6`](../runs/700607c95f112de6/scorecard.md)（H1，一次调用） |
| 候选 | [`runs/e6a372b2e05087b7`](../runs/e6a372b2e05087b7/scorecard.md)（H2 v1，最多 3 步，tool 方式） |
| 对比 | [`w2-vs-w1.md`](w2-vs-w1.md)：**关卡 FAIL**，自动通过区错误率 8.93% → 10.74% |
| 复现 | 在 Linux 上用回放模式复现了 owner 在 macOS 上的录制：1694 次录制命中，0 次模型调用 |

## 1. 循环"成功"了，路由却变差了

- 纠错成功率是 100%：第一次输出有 656 条不合格，循环之后一条不剩。
- 但路由分布从 280 / 344 / 414（通过 / 人工 / 打回）变成了 **326 / 11 / 701**，正好等于 W1 里模型自己给出的建议分布（pass 326、reject 701、manual_review 11）。

## 2. 矛盾全部是靠"改分数迁就建议"消除的

用回放逐条比对第 1 步和最终输出：

| 第 1 步：建议 / 分数所在区间 | 条数 | 怎么修的 | 最终区间 | 这些条目的真值 |
|---|---|---|---|---|
| reject / 转人工区 | 287 | 建议没变，**分数压进打回区** | 打回 | **222 条应通过（77%）**，65 条应打回 |
| pass / 转人工区 | 46 | 建议没变，**分数抬进通过区** | 通过 | 36 条应通过，**10 条应打回（22%）** |

333 条矛盾里，**没有一条**是通过修改建议来解决的。

对这个模型来说，`overallSuggestion` 才是它的判断，分数是事后给出的数字。分数落在中间区，恰恰是它不确定的信号：建议打回、分数却落在中间区的条目，77% 实际上应该通过。把这个信号"修"掉，等于拆掉了转人工这层保护。新进入自动通过区的条目错误率是 22%，自动打回区新增的条目错误率是 77%，两个关键指标因此一起变差。

## 3. 字段引用的修正不改变判断

只有 `unknown_field` 错误的条目有 323 条。修正之后，**路由一条都没有变**（打回 260、通过 53、人工 10），模型只是把字段发现重新挂到了真实存在的字段上。这一类修正是安全的，也有价值：生产环境里不会再写入无效的溯源记录。

## 4. 结论与可选方案

| 方案 | 做法 | 预期路由（用本次录制回放） |
|---|---|---|
| H2 v1（本次） | 所有错误都反馈给模型修正 | 关卡 FAIL（10.74%） |
| **H2 v2** | `suggestion_score_conflict` 和 `error_finding_on_pass` **只标记、不反馈**（确定性降级为 `manual_review`，并写入 provenance）；结构错误、维度错误和 `unknown_field` 仍然交给模型修正 | 与 H1 相同（8.93%，关卡通过）。两种错误同时出现的 239 条需要重新调用一次，以便只针对 `unknown_field` 修正；这 239 条的分数原本都在转人工区，需要实测确认分数不会被改动 |
| 不合入 H2 | 直接做 W3 | — |

对 W3 的输入：`agentLoop` / `agentSteps` 记录下来的"建议与分数矛盾"标记本身就是一个强信号，例如"建议打回 + 分数在中间区"的条目里 77% 应通过。策略层校准阈值时应该把它当作特征使用，而不是让模型把它抹掉。
